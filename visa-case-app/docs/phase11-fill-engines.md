## フェーズ11：在留期間更新許可申請書の差し込みエンジン（Issue #79）

> 旧：phase11-renewal-fill-engine.md

方針は `docs/phase11-excel-fill-decision.md`。本書は、**最初の様式（在留期間更新）で確立した「セル座標の特定方法」と「テストの書き方」**を記録する。
後続の #84（変更）・#86（認定）・#88（取得）は、本書の手順をそのまま踏襲する。

### 構成

| ファイル | 役割 |

### セル座標の特定方法（重要。後続の様式でも同じ手順）

#### 1. 入力欄は「ロック解除されたセル」である

公式様式の各シートは**シート保護**がかかっており、利用者が入力するセルだけが、セルの保護設定「ロック」を外してある（`protection.locked === false`）。
そのため、入力欄の座標は、ラベルの位置関係から推測せず、**ロック解除セルを機械的に列挙して**特定する。

```js
import ExcelJS from "exceljs";
const wb = new ExcelJS.Workbook();
await wb.xlsx.readFile("docs/official/<様式>.xlsx");
const ws = wb.getWorksheet("<シート名>");
// 結合セルの左上以外（slave）は除く
ws.eachRow({ includeEmpty: true }, (row) =>
  row.eachCell({ includeEmpty: true }, (c) => {
    if (c.isMerged && c.master.address !== c.address) return;
    if (c.protection?.locked === false) console.log(c.address, c.isMerged ? ws.model.merges.find((m) => m.startsWith(c.address + ":")) : "", c.value ?? "");
  }));
```

#### 2. ラベルとの対応は、行のラベル文字と照合する

ロック解除セルの行・列の近くにある日本語ラベル（項目番号・項目名）を、`docs/official-forms-research.md`（更新編） と同梱の様式で照合して、`formMapping.ts` の項目に割り当てる。ラベルを読むには、結合セルの左上のセルだけを出力すると見やすい（結合セルは、すべてのセルに左上と同じ値が返るため）。

#### 3. 書き込むのは、結合セルの「左上のセル」だけ

結合範囲の左上以外に値を書くと、表示されない。`renewal.test.ts` の「座標の整合テスト」が、全項目について、(a) ロック解除セルであること、(b) 結合セルの左上であること、(c) 同じセルを二重に指していないこと、を検査する。**対応表を作ったら、まずこのテストを通す**。

#### 4. 桁ごとに分かれた欄・年月日が分かれた欄

* 法人番号（13桁）・雇用保険適用事業所番号（11桁。4-6-1桁）は、**1桁ごとのセル**。`digitItems` が、数字だけを取り出して1文字ずつ書く。
* 生年月日などは、年・月・日が別のセル（ラベル「年」「月」「日」の左隣の入力欄）。`dateItems` が分けて書く（先頭のゼロは除く）。
* 表（在日親族6行・職歴6件）は、行ごとにセルを展開する。あふれた分は書かず、`warnings` に出す。

#### 5. 選択式（○を付ける）項目

様式の性別（男・女）・配偶者の有無（有・無）は、入力セルがなく、印刷された選択肢から選ぶ書式である。**ロック解除セルがない**ため、`PickItem`（選ばれた値に応じて、選択肢のセルの文字を書き換える）で扱う。性別は選ばれなかった側と「・」を空にし、配偶者は「有・無」を、選ばれた方だけにする。値が空なら何も変更しない。

#### 6. シート名

実際のシート名は Issue 本文の呼称と異なり、末尾に空白（全角を含む）がある。`sheetKey()`（NFKC 正規化＋空白除去）で照合する。

| 本Issueでの呼称 | テンプレートの実際のシート名 |
|---|---|
| 申請人等作成用1 | `申請人用（更新）１` |
| 申請人等作成用2Ｎ | `申請人用２Ｎ `（末尾に半角空白） |
| 所属機関等作成用1Ｎ | `所属機関用１Ｎ `（末尾に半角空白） |
| 所属機関等作成用2Ｎ | `所属機関用２N　`（末尾に全角空白） |

`申請人用１（裏）`（提出不要の案内シート）、`業種一覧`、`職種一覧` は差し込み対象外。

### 設計判断

* **差し込み値は文字列で書く。** 日付の年・月・日、資本金、給与なども、数値にせず文字列のまま書く（桁区切り・単位などの書式を、テンプレート側に任せるため）。
* **業種・職種は、番号のときだけ書く。** 様式は「業種一覧／職種一覧」の番号を記入する欄だが、案件DBの業種は自由記述のため。番号でない場合は空欄にして、`warnings` で知らせる（番号への変換は後続）。
* **職歴の並び順**は、左の列を上から下へ、続いて右の列を上から下へ。
* **活動内容詳細**は2行（1行ずつの結合セル）。改行で区切り、3行目以降は2行目に続ける（`warnings` を出す）。
* `warnings`：申請人情報が未確定（`buildTranscription` と同じ文言）、親族・職歴のあふれ、番号でない業種・職種、桁数の合わない法人番号等。
* `auto`／`confirm`／`entered`／`always_confirm` の区分は、画面側（#80）が `formMapping.ts` から得る。本モジュールは値の差し込みのみを行う。

### exceljs で読み書きすると失われるもの（既知の制限）

出力ファイルとテンプレートを比較して確認した結果。**A4（`paperSize=9`）・倍率・向き・シート保護・結合セル・入力規則（□／■）・印刷範囲・列幅・書式は保たれる**。一方、次は保たれない。

* `申請人用（更新）１` の**写真枠（図形「写真 Photo 40mm×30mm」）**。exceljs は画像以外の図形（`drawing`）を書き出さない。
* `所属機関用２N` の手動改ページ（62行目）とヘッダー・フッター。
* プリンター設定の埋め込みデータ（`printerSettings*.bin`）。用紙サイズ・倍率は別に保持される。

写真枠は、行政書士が写真を貼る目印であり、様式の本質的な記載事項ではないが、必要であれば、後続で（例：出力後の zip に `drawing1.xml` を戻す後処理）対応する。

### 目視確認について

受け入れ基準の「Excel／LibreOffice で開いてレイアウトを目視確認」は、**本Issueの作業環境では LibreOffice が起動できず（テンプレートそのものも読み込めなかった）、実施できていない**。構造の比較（上記）と自動テストまでを確認済み。マージ前に、行政書士または担当者が、出力ファイルを Excel／LibreOffice で開いて確認すること。

### テストの書き方（後続の様式でも同じ）

1. **座標の整合テスト**：対応表の全項目が、テンプレートのロック解除セルの左上を指し、重複がないこと（機械的に検査できるため、座標の取り違えを防ぐ）。
2. **差し込み結果のテスト**：ダミー値（実案件の個人情報は使わない）を全項目に与えて `fill…Excel` を呼び、バッファを `exceljs` で読み直して、代表的なセルの値を確認する。年月日・桁ごとの欄・表の2行目以降も確認する。
3. **無入力テスト**：空の入力で、テンプレートの全セルの値が変わらないこと（リッチテキストは、書式を除いた文字列で比較）。
4. **レイアウト保持テスト**：用紙（A4）・倍率・向き・シート保護・結合セルが保たれること。
5. **warnings のテスト**：未確定・あふれ・形式不一致で、期待の文言が出ること。

セルの値の比較には、`renewal.test.ts` の `plain()`（リッチテキストを文字列にする）と `text(wb, シート名, セル)` を使う。テストは、各ケースで差し込みに1秒前後かかる（テンプレートが大きいため）。ケースを増やす場合は、1テスト5秒の上限に注意する。

### #80（画面・生成履歴への統合）への引き継ぎ

* `fillRenewalExcel` は Node.js ランタイム専用。API ルートには `export const runtime = "nodejs"` を指定する。
* Vercel 等では、`docs/official/*.xlsx` が、ファイル追跡の対象に入らない可能性がある。API ルートで使う際は、`next.config.ts` の `outputFileTracingIncludes` に `docs/official/**/*.xlsx` を指定し、本番相当の環境で読み込めることを確認する。
* ダウンロード画面には、出典（出入国在留管理庁）・加工している旨・「下書きであり、提出前に原本と照合する」旨を表示する（`docs/official/README.md` の利用条件）。
* `formMapping.ts`（転記補助シート）の廃止は #80 の範囲。本Issueでは変更していない。

## フェーズ11：在留資格変更許可申請書の差し込みエンジン（Issue #84）

### 更新様式との座標の違い（重要）

変更様式の4枚のうち、**項目は更新と同じでも、セルの位置が異なる**シートがある。更新の座標を流用せず、ロック解除セルの列挙から特定した。

| シート（実際の名称） | 更新との違い |
|---|---|
| `申請人用（変更）１` | 項目の並びが異なる（出生地・配偶者の位置、13に「希望する在留資格」と「在留期間」の2段、14変更の理由）。在日親族の表は68行目から（更新は64行目から） |
| `申請人用２Ｎ ` | 更新より行番号が1小さい。取次者の下段（所属機関等・電話番号）のみ2小さい（77行目） |
| `所属機関用１Ｎ ` | 更新より列が2つ左（例：名称 G24→E24、法人番号 T〜AF→R〜AD）。行は同じ |
| `所属機関用２N　 ` | 更新と同じ位置 |

`申請人用１（裏）`・`業種一覧`・`職種一覧` は差し込み対象外。シート名は末尾に全角を含む空白があるため、`sheetKey()`（NFKC＋空白除去）で照合する（#79 と同じ）。

### 設計判断

* **13 希望する在留資格**は、`CaseRecord.targetStatus`（案件情報の「変更後の在留資格」）を、そのまま書く。二重入力しないための #83 の方針。これを差し込みへ渡すため、`FillInput` と `OfficialFormContent["input"]` に任意の `targetStatus` を追加した（`officialFormInputOf`・`parseFillInput` も対応）。`FILLERS` の関数の引数に `targetStatus` を足したが、更新の関数は3引数のまま使える。
* **14 変更の理由**は `FormDetails.changeReason` を書く。`renewalReason` は書かない。**5 出生地**は `placeOfBirth`。
* **対象範囲**（`CHANGE_SPEC.isInScope`）は、Issue の要件どおり `procedureType === "change"` のみ。現在の在留資格は問わない（変更は、現在の在留資格が技術・人文知識・国際業務とは限らないため）。
* 様式は技術・人文知識・国際業務向け（申請人等作成用1・2N、所属機関等作成用1N・2N）。**変更後の在留資格が技術・人文知識・国際業務でない**場合と、**未入力**の場合は、`fillChangeExcel` が `warnings` に出す（生成は妨げない）。画面の事前表示（`officialFormScopeWarnings`）は現在の在留資格・手続種別のみを見るため、この警告は生成時にのみ出る。
* 法人番号・雇用保険適用事業所番号の桁数検査は、更新と同じ（`RENEWAL_DIGIT_CHECKS` を再利用）。警告の文言（申請人情報の未確定・あふれ・番号でない業種・職種）も更新と同じ。
* 更新の `renewalMapping.ts` は変更していない。小さな補助関数（日付分解・1桁ずつの欄など）は `changeMapping.ts` に同じものを置いた（並行する #86・#88 との競合を避けるため。共通化は別課題）。
* 既存テスト `tests/officialForm.test.ts` は、「変更は専用様式がない」ことを前提にしていた2か所を、専用様式がない手続種別（`other`）に変えた。変更の差し込みの確認を追加した。
* 過去に保存した公式様式の版（`content_json.officialForm.input`）には `targetStatus` がない。変更の版を再生成（ダウンロード時の再作成）しても、項目13は空欄になる。#80 の公式様式は更新のみだったため、実害は想定しない。

### 設計判断

* **書くのは「入力欄のうち、案件DBに対応する値があるもの」だけ**（更新と同じ）。値は文字列で書く（日付の年・月・日、金額も数値にしない）。

* **性別・配偶者の有無は選択式（`PickItem`）**。更新と同じく、選ばれなかった側と「・」の文字を空にする。認定は、性別が `E23`・`G23`・`H23`、配偶者が `AK23`・`AM23`・`AN23`（更新は配偶者が結合セル1つ `Y21`）。配偶者は「有」「無」の文字がそれぞれ別セルのため、更新と書き換え方が異なる。同伴者(15)・出入国歴(17)・認定申請歴(18)・犯罪処分(19)・退去強制歴(20)・在日親族の有無(21)・同居予定の有無（`V95` など「有・無」）の○は、Issue の方針どおり対象外。
* **対象範囲の判定（`COE_SPEC.isInScope`）は手続種別のみ**。認定は海外からの呼び寄せで、現に有する在留資格がない。判定に使える入国目的（`targetStatus`）は、`OfficialFormScope` に含まれていない。含めると画面・履歴の共通コードに触れるため（#84・#88 と衝突する）、本Issueでは行わない。このため、入国目的が様式（Nシート＝技術・人文知識・国際業務、高度専門職1号イ・ロ、研究、介護、技能、特定活動の一部が対象）の対象外でも、注意は出ない。行政書士が、様式選択表（`申請人用（認定）１（裏)`）で確認する。

### 様式 I・L・M・U への対応（Issue #187・#191）
- 高度専門職は、号と行う活動から様式（I・L・M・N・U）を決め（`lib/hspForm.ts`）、その雛形で出力する。高度専門職ではない「経営・管理」は、様式 M を使う。
- 第1表（申請人用（認定）・同（裏））は全様式共通のため、`coeMapping.ts` を使う。第2表以降は、様式 N が `coeMapping.ts`、I・L・M・U が `coeTable2.ts`。様式ごとにセルの位置も項番も異なるため、N の表は流用しない。
- `coeTable2.ts` は、様式ごとの座標の仕様（`SPECS`）から差し込み項目を組み立てる。座標は、雛形の「ロック解除セル」から特定し、`coeTable2.test.ts` が、全項目が入力欄の左上を指すこと、同じセルを2項目が指さないこと、「月額」の□の位置を検査する。
- 案件情報に項目がない欄は、差し込まず、様式ごとの `manual`（`warnings` の文言）で案内する。項目の追加は、行政書士と欄の対応を確認してから、別途行う。
  - M：契約の形態、財産の総額、申請人の投資額、法人税納付額、常勤従業員のうち日本人等の数、日本語能力者の有無、就労予定期間、事業所の面積・保有の形態
  - L：派遣元（転勤元）の会社・関係、契約の形態、派遣・就労予定期間
  - I：専攻・専門分野、教育に係る欄（26〜28）、契約の形態、稼働先、研究室、就労予定期間、雇用形態
  - U：活動内容の区分（22）、経歴・在学中の大学名・具体的な在留目的・専攻、起業関連の経験、契約の形態、活動内容の区分、就労又は就学予定期間、雇用主・扶養者・サポーター
- 変更・更新の「経営・管理」は、経営・管理用の様式（第2表以降）の雛形を、この環境から入手できなかった（入管庁サイトが 403）ため、第1表のみ差し込み、第2表以降は様式上で記入するよう警告する。雛形を `docs/official` へ追加すれば、同じ方式で拡張できる。
- #186（ポイント計算表）と共有する入力項目（学歴・職歴・年収など）は、本 Issue では既存の `FormDetails` の項目を使った。#186 で項目を追加する際は、同じ項目を共有すること。

### 設計判断・対象外

* 性別・配偶者の有無は、#79 と同じ「選択肢の文字を書き換える」方式(`PickItem` 相当)。取得様式の配偶者欄は3つの別セル(AH21・AI21・AJ21)で、更新様式(結合セル Y21)と異なる。
* **11 その他の内容(Z36)** は、`acquisitionCause === "other"` のときだけ書く。**13 その他(Q44)** は、`targetStatus` が4つの在留資格(チェックボックスのあるもの)以外のときだけ、その在留資格名を書く。
* **`targetStatus` は、#84(変更の差し込み)で差し込み経路(`OfficialFormContent["input"]`・`officialFormInputOf`・`parseFillInput`・`FillInput`・`Filler` の第4引数)に通された。** `FILLERS` の取得の関数は、その `targetStatus` をそのまま `fillAcquisitionExcel(a, f, targetStatus)` に渡す。そのため、画面から生成した取得様式でも、13 の「その他」欄と13の warning が出る。ただし、#84 より前に保存した版には `targetStatus` がないので、再生成すると13は空欄になる。
* **17 代理人の携帯電話番号(Y79)** は、案件DBに項目がないため対応表に含めない(別Issue。`docs/official-forms-research.md`（取得編）の3章)。
* 差し込み値は文字列。入力のない項目は、テンプレートの元の状態のまま。`warnings` は、申請人情報が未確定、親族のあふれ、取得の事由・希望する在留資格のチェックの案内。
* 取得様式の対象判定(`ACQUISITION_SPEC.isInScope`)は、手続種別が `acquisition` であれば対象とする(様式は在留資格を限定しない)。

## フェーズ15：チェックボックス・有無の○（丸選択）の差し込み対応

> 旧：phase15-checkbox-pick-fill-engine.md

本書の更新編（#79）・変更編（#84）・認定編（#86）・取得編（#88）は、いずれも「チェックボックス（□）」「有無の○（有・無、はい・いいえ）」の差し込みを、Issue の方針により対象外としていた（行政書士が様式上で手動選択する前提）。

本フェーズは、利用者（行政書士）からの明示の指示「チェックボックスや該当箇所に丸をつけるところも、反映がされてさないので直してください」を受け、**その方針を転換し、4様式すべてでチェックボックス・有無の○を実際に差し込む**。対象外のまま残すのは、案件DBに対応する入力がない項目、および原本のプルダウンが号・種別まで区別できない一部のCOE選択肢のみとする。

以下の各節で「対象外」としていた記述は、本フェーズにより更新されている。本書は、その更新内容をまとめて記録する。

### 対象にした項目

既存の `PickItem`（「選ばれた側だけを残す」仕組み。`renewalMapping.ts`）を、そのまま拡張して使った。新しいパターンを作らず、既存の4パターン（単一セル書き換え・3分割セル・詳細欄つき5分割セル・注記文埋め込み）に、チェックボックス一覧（□→■）のパターンを1つ追加しただけである。

| 様式 | 新たに差し込む項目 |
|---|---|
| 更新 | 15 犯罪を理由とする処分の有無、16 在日親族及び同居者の有無、在日親族各行の同居の有無（6行） |
| 変更 | 15 犯罪を理由とする処分の有無、16 在日親族及び同居者の有無、在日親族各行の同居の有無（6行） |
| 認定 | 11 入国目的（チェックボックス34個）、15 同伴者の有無、17 過去の出入国歴の有無、18 過去の認定証明書交付申請歴の有無、19 犯罪を理由とする処分の有無、20 退去強制又は出国命令による出国の有無、21 在日親族及び同居者の有無、在日親族各行の同居予定の有無（4行） |
| 取得 | 11 在留資格取得の事由（チェックボックス3個）、13 希望する在留資格（チェックボックス4個＋その他）、14 犯罪を理由とする処分の有無、在日親族各行の同居（4行。「はい・いいえ」表記） |

いずれも、値が未入力（空文字）の場合は、テンプレートの元の状態（`有・無`・`はい・いいえ`・`□` のまま）を変更しない。`PickItem.writes` に対応するキーがなければ何もしない、という既存の仕組みをそのまま使っているため、空欄のセルを誤って消す・書き換える心配はない。

### チェックボックスの表現：「■」（U+25A0 BLACK SQUARE）

原本の印刷済み文字は「□」（U+25A1 WHITE SQUARE）。選択を示すため、該当のセルの文字を「■」（黒四角）に置き換える方式にした。

* 原本のフォント（ＭＳ Ｐ明朝）は「■」を問題なく表示できることを確認済み。
* 対象のチェックボックスセル（COE項目11、取得の項目11・13）は、`openpyxl` で確認した結果、原本側で `protection.locked == False`（ロック解除）になっている。つまり、様式の設計自体が「ここは人が直接書き込む欄」として想定しているセルであり、■への置き換えは様式の意図に沿っている（既存の性別・配偶者等、ラベル文字を書き換える方式のセルはロックされたままで、挙動が異なる。各様式の `*.test.ts` で、ロック状態をチェックボックス欄とそれ以外に分けて確認している）。
* 選ばれなかった他のチェックボックスは、**そのまま「□」として残す**（空文字にしない）。複数の□のうち1つだけを■にする、という原本の見た目に最も近い表現のため。

### 認定（COE）項目11「入国目的」：34択のうち、曖昧さのない場合だけチェックする

認定の項目11は、34個のチェックボックスから1つを選ぶ方式（`coeMapping.ts` の `COE_PURPOSE_CHECKBOXES`）。案件の「希望する在留資格」（`targetStatus`。`lib/types.ts` の `RESIDENCE_STATUSES` という固定のプルダウン値）と、様式の選択肢の文字列が**一字一句完全に一致する場合だけ**、該当の□を■にする。

一致しない場合（プルダウンにない表記、または下記の号・種別まで様式側で区別が必要な場合）は、チェックを付けずに `warnings` で案内する。これは、不正確な選択を公的書類に書き込むリスクを避けるための判断である。

* 高度専門職の号（1号イ／ロ／ハ）は、案件の「希望する在留資格」（変更は「変更後」）で2段階に選べる（Issue #181）。保存値は様式の選択肢と同じ文字列（例：「高度専門職（1号ロ）」）で、DB の変更はない。一致した号の□だけが■になり、号が未選択の「高度専門職」は、チェックなしで「号を選択してください」と警告する。「特定技能」「技能実習」「特定活動」は、案件側で号・種別まで持たないため、従来どおり一致せず警告が出る（別途検討）。「行う活動」は、認定の申請書の補足情報（`FormDetails.hspActivity`。DB の変更なし）で選び、号との組み合わせから使う様式（I・L・M・N・U）を `lib/hspForm.ts` の対応表で決める（表にない組み合わせは「様式を特定できません」と表示し、推測しない）。決まった様式のテンプレート（`COE_TEMPLATE_PATHS`。`docs/official/` に取り込み済み）を使って出力する。第1表（申請人用（認定）。入国目的の■を含む）は、5様式で同じ配置のため、同じ対応表で差し込む。第2表以降は、様式 N（`coeMapping.ts`）と、I・L・M・U（`coeTable2.ts`。Issue #187・#191）にそれぞれ対応表があり、様式ごとに別の座標で差し込む（N の表を流用しない）。案件情報に項目がなく差し込めない欄（契約の形態、派遣元、就労予定期間、活動内容の区分など）は、様式ごとの一覧を `warnings` で案内し、様式上で記入する。行う活動が未選択、または表にない組み合わせの場合は、様式 N の第1表のみ差し込み、様式の確認を警告する。
* 「その他」の□も、案件側に対応する入力欄（自由記述）がないため、対象外のまま。

### テストでの確認観点

各様式の `*.test.ts` に、次の観点を追加した（`acquisition.test.ts` が先行実装、`renewal.test.ts`・`change.test.ts`・`coe.test.ts` も同じ方針）。

* 新しい `PickItem` の `no` 一覧が、実装した項目数と一致すること（既存の座標整合テストの延長）。
* 「有」「無」それぞれを選んだ場合に、選ばれた側の文字が残り、もう一方と「・」が消えること。
* 入力がない（相手がいない・該当者がいない）行は、原本の元の表記（`有・無`・`はい・いいえ`）がそのまま残ること（空文字にならない）。
* チェックボックス形式は、選ばれた□だけが「■」になり、他の□は「□」のまま残ること。
* 認定の入国目的は、一致する場合に■が付き、一致しない（号・種別が必要）場合はどの□にも触れず、`warnings` に案内が出ること。

### 目視確認

LibreOffice（`soffice --headless --convert-to pdf`）でダミーデータを差し込んだ4様式を変換し、PDFを画像化して確認した。性別・配偶者の有無（既存）、犯罪歴・在日親族の有無とその注記文、在日親族各行の同居（有・無／はい・いいえ）、COE項目11の■とその他の□、取得の事由・希望する在留資格の■と□が、いずれも意図どおり表示されることを確認した。
