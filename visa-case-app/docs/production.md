# 本番運用ガイド（フェーズ7）

在留カード・パスポート情報などの個人情報を扱うため、開発環境と本番環境を完全に分離します。

## 1. 環境の分離

| 項目 | 開発環境 | 本番環境 |
| :-- | :-- | :-- |
| データ | ダミーデータのみ | 実案件データ |
| Supabase | 開発用プロジェクト | 本番用プロジェクト |
| 環境変数の設置場所 | `.env.local`（Git管理外） | Vercel の Environment Variables（Production） |
| デプロイ | `npm run dev` / Vercel Preview | Vercel Production |

規則：
- 実案件のデータ・書類画像を、開発環境・Preview環境へ入力しない。
- Vercel の Preview 環境には、本番用の Supabase 接続情報を設定しない（Preview は開発用プロジェクトを指す）。
- 本番用 Supabase の管理者アカウントには、多要素認証を設定する。

## 2. 環境変数一覧

| 変数 | 公開 | 内容 |
| :-- | :-- | :-- |
| `NEXT_PUBLIC_SUPABASE_URL` | 可（ブラウザへ公開） | Project URL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 可（RLSで保護） | Publishable（anon）キー |

設定してはならないもの：`service_role` キー、`sb_secret_` で始まる鍵、データベースのパスワード。
`lib/env.ts` が起動時に検証し、秘密鍵が混入している場合は接続を拒否します。

## 3. 設定漏れ時の動作
- 開発（`next dev`）：未設定ならブラウザ内の仮データで動作します。
- 本番（`next build` / `next start`）：未設定・形式不正の場合は、仮データへ切り替えず、画面全体に設定エラーを表示して停止します。

## 4. 公開前チェックリスト
- [ ] 本番用 Supabase プロジェクトを新規作成した（開発用と別）
- [ ] `supabase/migrations` を番号順にすべて実行した
- [ ] 新規ユーザー登録（Allow new users to sign up）を無効にした
- [ ] Security Advisor に、未対応の警告がない
- [ ] 全テーブルでRLSが有効である
- [ ] Storage の `documents` バケットが非公開である
- [ ] バックアップを確認した（Pro プランの場合は PITR の要否を判断）
- [ ] 管理者アカウントに多要素認証を設定した
- [ ] Vercel の Production にのみ、本番用の環境変数を設定した
- [ ] 他事務所のデータへアクセスできないことを、2つのアカウントで確認した

## 5. エラー表示の方針
Supabase の内部エラー文（テーブル名・制約名など）は画面へ表示しません（`lib/errors.ts`）。画面には一般的な文言のみを表示し、コンソールにはエラーコードのみを残します。

## 6. 監査ログの方針
- 記録するもの：操作したユーザー、案件、操作の種類、変更された項目名、日時、成否。
- 記録しないもの：氏名・住所・パスポート番号・ファイル名・メモ本文・日付などの値。`lib/auditDetail.ts` が、項目名・ID・列挙値以外を破棄します。
- 閲覧は同じ事務所の所属者のみ（RLS）。修正・削除はできません（追記専用）。
- 案件を削除しても監査ログは残します。保存期間と削除の方針は、運用開始前に決定してください（未決定）。

## 7. セキュリティヘッダー
`next.config.ts` で、全ページへ次を付与しています。
- フレーム埋め込みの禁止（`frame-ancestors 'none'`、`X-Frame-Options`）
- `X-Content-Type-Options: nosniff`、`Referrer-Policy`、`Permissions-Policy`（カメラ・位置情報などを無効化）
- `Strict-Transport-Security`（HTTPS のみ）

`script-src` を制限する厳格な CSP は、Next.js のインライン処理や PDF プレビューへの影響を検証したうえで、別途導入します（未実施）。

## 9. 複数ユーザーと役割（フェーズ10）
`supabase/migrations/0013_roles.sql` を、0001〜0012 の実行後に実行します。実行前にバックアップを取り、ファイル冒頭の確認クエリが 0 であることを確かめてください。既存の所属者は、すべて所有者（owner）のまま変わりません。

| 役割 | 閲覧 | 案件の作成・編集、書類・文書の管理 | 案件の削除 | メンバーの追加・削除 | 役割の変更・事務所名の変更 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| owner（所有者） | ○ | ○ | ○ | ○ | ○ |
| admin（管理者） | ○ | ○ | ○ | △ 担当者・閲覧のみ | × |
| staff（担当者） | ○ | ○ | × | × | × |
| viewer（閲覧のみ） | ○ | × | × | × | × |

- メンバーの追加は、**すでにアカウントがある方**のメールアドレスを指定して行います（招待メールは送信しません）。相手がこのシステムに初めてログインした際に自動作成された空の事務所は、追加時に整理されます。案件のある別の事務所に所属している方は追加できません。
- 最後の所有者は、降格も削除もできません（データベース側で拒否）。
- 追加・役割変更・削除は、監査ログに記録されます（メールアドレスは記録せず、対象のユーザーIDと役割のみ）。
- 担当者は、書類の差し替えやチェック項目の削除など、案件の子データの削除ができます。**ファイル保存先（documents）の削除も担当者に許可しています**。案件そのものの削除は、所有者・管理者に限ります。
- 画面の表示制限は補助です。実際の拒否は、データベースの規則が行います。
- 確認手順は `docs/phase10-role-test.md` を参照してください。
- 顧客ポータル（client 役割）は未実装です。設計は `docs/phase10-client-portal-design.md` にあります。
