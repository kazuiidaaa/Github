# 顧客ポータル 設計書（未実装）

本書は設計のみです。実装は、フェーズ7の本番セキュリティ確認（RLS・Storage・バックアップ）と、複数ユーザーの権限管理（0013）の運用確認が済んでからにしてください。

## 1. 目的と原則
- 顧客（申請人本人、または所属機関の担当者）が、行政書士からの依頼に沿って**書類を提出し、進捗を確認する**ためのもの。
- 顧客に案件の全情報は見せない。**見せるものを列挙して許可する（許可リスト）方式**とし、既存テーブルへの直接の参照権限は与えない。
- 法的な判断（申請の可否、許可の見込み）は表示しない。

## 2. 顧客に見せるデータ
| 区分 | 内容 | 出どころ |
| :-- | :-- | :-- |
| 必要書類一覧 | 書類名、提出状況、期限、顧客向けの説明文 | `requirement_states`・規則（顧客向け表示名のみ） |
| アップロード依頼 | 行政書士が「顧客に依頼する」と指定した書類 | 新規：`client_requests` |
| 提出済み書類 | 顧客自身がアップロードしたファイルの名前と日時 | 新規：`client_uploads` |
| 行政書士からの連絡 | 行政書士が顧客向けに書いたメッセージ | 新規：`client_messages` |

見せないもの：申請人情報の詳細、在留カード番号、雇用・会社情報の詳細、申請前チェック、内部確認シート、監査ログ、メモ、他の案件。

## 3. 役割と紐付け
- `members.role` に `client` を追加せず、**別テーブル `client_access`** で管理する（事務所の所属者と顧客のアクセス範囲を混ぜない）。
  - `client_access(user_id, organization_id, case_id, created_by, expires_at, revoked_at)`
- 顧客は事務所の `members` に入らない。`is_member` / `has_role` は顧客を通さない（既存の規則に影響しない）。
- アクセスは**案件単位**で付与し、期限（`expires_at`）と取り消し（`revoked_at`）を持つ。案件の完了時に自動で失効させる運用を基本とする。

## 4. 認証
- 顧客は個別のアカウントでログインする。共有リンクのみでのアクセスは採用しない。
- 初回は、行政書士が顧客のメールアドレスを登録し、**一度限りのリンク**（有効期限つき）から、パスワードまたはメールの確認コードで本人確認をする。
- 顧客のアカウントには、事務所側と同じ Supabase プロジェクトを使うが、**ログイン後に表示する画面とAPIは別系統**（`/portal` 配下）とする。
- 多要素認証の導入可否を、運用開始前に判断する。

## 5. 権限（RLS）の方針
- 顧客向けのテーブルは `client_access` を参照し、`user_id = auth.uid()` かつ有効期限内・未取り消しの案件に限る。
- 既存テーブル（`cases`、`applicants`、`documents` など）に、顧客向けのポリシーは**追加しない**。顧客向けの表示は、顧客向けテーブルまたは `security definer` の関数（返す列を固定）で提供する。
- 顧客のファイルアップロードは、専用バケット（例：`client-uploads`）の「事務所ID/案件ID/顧客ID/ファイル名」パスに限る。閲覧は自分のアップロード分のみ。更新・削除は不可（差し替えは新しいファイルとして追加）。
- ファイルサイズ・MIMEタイプの制限を設ける。ウイルス検査の要否を判断する。
- 事務所側は、顧客のアップロードを確認してから、案件の書類として取り込む（自動で既存の書類へ反映しない）。

## 6. 画面案（`/portal`）
1. 案件の一覧（アクセス権のある案件のみ）
2. 案件の画面：依頼された書類、提出状況、アップロード欄、連絡欄
3. 注意書き：「ここに表示される内容は、提出状況の確認用です。申請の可否や結果を示すものではありません。」

## 7. 監査
- 顧客のログイン、アップロード、メッセージ送信を `audit_logs` に記録する（個人情報・本文は記録しない）。
- 事務所側で、顧客のアクセス付与・取り消しを記録する。

## 8. 実装前に決めること
1. 顧客の本人確認の強さ（確認コード、多要素認証の要否）
2. 顧客のアカウントの有効期間と、案件完了時の扱い
3. アップロードできるファイルの種類・容量・ウイルス検査
4. 顧客向けメッセージの保存期間と削除方針
5. 個人情報の取扱い（利用目的の通知、同意の取得方法）を、事務所の方針に合わせて確定
6. 顧客に見せる書類名の表記（内部名称と分けるか）

## 9. テスト方針
- 顧客Aが、顧客Bの案件・ファイル・メッセージを取得できないこと。
- 顧客が、既存の全テーブル（`cases` ほか）を select できないこと。
- 期限切れ・取り消し済みのアクセスが拒否されること。
- 事務所の所属者でない顧客が、メンバー管理の関数を呼べないこと。
