# 役割別の確認手順（0013_roles.sql の適用後）

開発用の Supabase プロジェクトで実施してください。実案件のデータでは行わないでください。

## 準備
1. アカウントを3つ用意する：A（既存の所有者）、B、C。B と C は、一度ログインして、自動作成された空の事務所がある状態にする。
2. A でログインし、アカウント画面の「メンバー管理」から、B を「担当者」、C を「閲覧のみ」で追加する。
3. 案件を1件作成し、在留カード画像を登録しておく。

## 画面での確認
| 操作 | A（所有者） | B（担当者） | C（閲覧のみ） |
| :-- | :-- | :-- | :-- |
| 案件一覧の「新規案件」 | 表示 | 表示 | 非表示 |
| 案件詳細の「削除」 | 表示 | 非表示 | 非表示 |
| 書類タブのアップロード | 表示 | 表示 | 非表示 |
| 申請人情報・雇用・必要書類・チェックの入力 | 可 | 可 | 無効（閲覧のみの表示） |
| 申請書類の生成 | 可 | 可 | 不可 |
| メンバー管理の欄 | 表示 | 非表示 | 非表示 |

## データベース側の拒否の確認（画面を迂回した操作）
SQL Editor では、実行ロールが postgres になり規則を迂回します。**アプリにログインしたブラウザの開発者ツール、または各ユーザーの JWT を使った API 呼び出し**で確認してください。

| 操作 | 期待される結果 |
| :-- | :-- |
| C が `cases` を update / insert する | 拒否（0件、または権限エラー） |
| B が `cases` を delete する | 0件（拒否） |
| B が `documents` の行を delete する | 許可 |
| C が `storage.objects`（documents）へ upload する | 拒否 |
| B が他事務所の案件IDを含むパスへ upload する | 拒否 |
| B が `add_member_by_email` を呼ぶ | `forbidden` |
| 管理者が `add_member_by_email` で admin を指定する | `forbidden` |
| 管理者が owner を `remove_member` する | `forbidden` |
| owner が最後の owner を `set_member_role` で降格する | `last owner` |
| 存在しないメールアドレスを追加する | `cannot add member`（存在の有無が分からないこと） |
| 案件のある別事務所の所属者を追加する | `cannot add member` |

## 監査ログ
メンバーの追加・役割変更・削除が、アカウント画面の監査ログに表示されること。メールアドレスが記録されていないこと（`audit_logs.detail` に `targetUserId` と `role` のみ）。
