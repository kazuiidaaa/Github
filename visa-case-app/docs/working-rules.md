# 作業規則（詳細）

`CLAUDE.md` の要点の詳細を、ここに記す。

## 課題と作業記録（Issue の運用）
課題は、利用者または調整のセッションが、GitHub の Issue として書く。担当者（Claude）は、次の手順で作業する。

### Issue の起票
- 担当者は、独自の判断で、新しい Issue を起票しない。Issue は、利用者または調整のセッションのみが起票する。
- 実装のセッションは、見つけた課題を、提案として、作業中の Issue のコメントに書くのみとする。

### 作業の開始時
- 未完了（open）の Issue を読み、着手する課題を確認する。
- 前の Issue からの引き継ぎがある場合は、前の Issue の5項目のコメントのみを読む。作業の経過（過去のやり取り）は、読まない。
- 課題が不明確な場合は、着手せず、Issue 上で質問する。

### 作業の終了時
着手した Issue に、次の項目で1コメントを書く。見出しは `日付｜担当者（役割名）｜ブランチまたは PR`。
1. 行ったこと
2. 判断とその理由
3. 未完了の事項
4. 次の担当者への引き継ぎ
5. 確認した結果（テスト・動作確認など）

- 各項目は1〜3行とする。次の担当者が、これだけ読めば着手できる長さにする。
- 完了した場合は、PR の説明に `Closes #番号` を記載し、Issue と結び付ける。
- 実案件の氏名・住所・番号などの個人情報は、Issue にも書かない。
- 設計や運用方針の決定事項は、docs/ にも残す。

### セッションの区切り
- 1つのセッションで担当する Issue は、1〜2件までとする。
- 1件が終わったら、5項目のコメントを書き、セッションを切り替える。

## ブランチとプルリクエストの運用
複数の担当者（セッション）が同じブランチを使うと、コミット・プルリクエストの本文・レビューが混ざり、切り戻しとレビューが難しくなる。これを避けるため、次の規則に従う。
この規則は、セッション開始時に指定されたブランチ名より優先する（利用者の許可済み）。

### 着手前
- 対象の Issue に、既存のブランチやプルリクエストがないかを確認する。ある場合は、重複して着手せず、Issue 上で状況を確認する。
- Issue 本文に着手順の指定（例：「#26・#30 の完了後に着手」）がある場合は、守る。
- 指定されたブランチが、次のいずれかに当てはまる場合は、そのブランチを使わない。
  - 開いているプルリクエストが、すでにある。
  - 自分のものではない、未マージのコミットがある。
- 使わない場合は、新しいブランチを作成する。

### ブランチ
- ブランチは、1つの Issue または1つの目的につき、1本とする。
- 名称は `claude/issue-<番号>-<要約>` とする（例：`claude/issue-29-date-input`）。Issue がない場合は、`claude/<要約>` とする。
- 他の担当者が使っているブランチへ、プッシュしない（統合用ブランチを除く。次の節）。
- マージ済みのブランチは、再利用しない（統合用ブランチを除く）。

### 統合用ブランチ
- 「Claudeさん用1」「Claudeさん用2」を、統合用のブランチとして使う。
- 作業用のブランチ（`claude/issue-<番号>-<要約>`）は、統合用のブランチから分岐させ、PR の向き先も統合用のブランチとする。
- 統合用のブランチから main へは、まとまった段階で PR を出す。含む Issue は、すべて `Closes #番号` で列記する。本文1行目の「競合なし／競合あり」は、main に対する判定とする。
- main が更新されたときは、統合用のブランチに main をマージで取り込み、競合を確認する。履歴の書き換えと強制プッシュは、禁止とする。
- 統合用のブランチは、マージ後も再利用する。
- 当面の使い分け：用1は #263〜#266（新規登録、案件詳細）、用2は #260〜#262、#267、#268。
- 統合用のブランチへ向ける PR は、本文1行目に、向き先のブランチに対する競合の有無を書く。

### プルリクエスト
- 1つのプルリクエストには、1つの目的のみを含める。ただし、統合用のブランチから main への PR は、含む Issue をすべて列記してよい。
- 本文は、作成した担当者のみが編集する。他の担当者の記載を、上書きしない。
- 下書き（draft）で作成し、`Closes #番号` を記載する。
- PR の数は、必要最小限とする（デプロイの検査に回数制限があるため）。

### プッシュ前
- `git fetch` で、リモートの同名ブランチの先頭を確認する。自分のものではないコミットがある場合は、プッシュせず、別のブランチへ切り替える。
- 競合が起きた場合、他の担当者のコミットを、`reset --hard` や強制プッシュで消さない。

## プルリクエストの報告の書き方
利用者はコードを読まない。確認に必要なことだけを、平易な言葉で伝える。
- 本文の最初の1行に、競合の有無を「競合なし」または「競合あり」と書く。GitHub 上の PR の状態（mergeable）で確認し、推測で書かない。確認できなかった場合は、その旨を書く。
- 競合がある場合は、担当者が解消してから報告する。
- 利用者の確認が必要な場合のみ、利用者（@kazuiidaaa）をメンションする。不要な場合は、メンションしない。
- 内容の説明は、コードではなく、画面で何が変わるか、業務への影響があるかを書く。
- 利用者が AI によるレビュー用のボットを使わない方針のため、外部のボットは導入しない。
